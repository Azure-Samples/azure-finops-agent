## [0.4.0] - 2026-10-27

### Added

- Add an in-app feedback form that files GitHub issues. **Have feedback?** sits in the top bar on every page (**Feedback** on phones) and under the message box, and every finished answer has a **Feedback** button that reads **Tell us what went wrong** after a **Poor answer** rating. The form asks for a type (bug, idea, answer quality, other), a summary and optional details. Feedback about an answer carries the rating, and the question it answered only if the user ticks **Include the question I asked**.
  - **How issues are created.** New `GET /api/feedback/config` and `POST /api/feedback` endpoints create the issue through a GitHub App: the host signs a short-lived JWT with the app's private key and exchanges it for an installation token limited to `issues: write` on the one configured repository. The token is kept in memory until five minutes before it expires. The key and tokens never reach the browser, logs or responses, and GitHub's own error text is never relayed. Issues get a `feedback` label, plus `bug` or `enhancement`, and their footer names the type, rating and build. When no app is configured or installed, the form opens the new `feedback.yml` issue form with the feedback filled in, so the user posts it with their own account; customer deployments work this way with no setup. The link sets no `labels` parameter, because GitHub answers 404 when the user may not set it; the form's own `feedback` label applies instead.
  - **Privacy and abuse controls.** The issue is public, so the server refuses secrets, IDs (GUIDs), email addresses and IP addresses before anything is sent. The refusal names the kind of content without echoing it. @mentions cannot notify anyone. Each browser can create 3 issues in 10 minutes and 10 a day, and the process at most 60 an hour.
  - **Accessibility.** The dialog traps focus, closes with Escape or its backdrop, returns focus to the button that opened it, keeps an unsent draft per subject, moves focus to the field the server refused, and links only to `https://github.com/` addresses. It asks the server for the mode when the page loads and says which path it will take only once the server has answered.
  - **Configuration.** `GitHubFeedback:AppId`, `GitHubFeedback:PrivateKey` (PEM, `\n`-escaped PEM or base64) and `GitHubFeedback:Repository` (default `Azure-Samples/azure-finops-agent`), with `GITHUB_FEEDBACK_APP_ID`, `GITHUB_FEEDBACK_PRIVATE_KEY` and `GITHUB_FEEDBACK_REPOSITORY` for `azd`.
- Add an extended evaluation tier and make every evaluation result visible as red or green. The deployment gate is unchanged (23 scenarios, all must pass, nothing else can block a release), but only 23 of the 130 catalog scenarios ever ran. A new **AI quality report** workflow (`ai-quality-report.yml`, Monday 03:00 UTC and on demand) runs the ten most important of them through the same handler, tools and judge, chosen from a library of 170 in `tests/LiveEvaluations/scenarios.mjs`: the other 107 catalog scenarios plus about 60 new synthetic ones (see below). It is a separate workflow because the gate workflows forbid `continue-on-error`; no deployment depends on it, it waits up to 30 minutes for running deployment workflows and then pauses before every case while one runs (both tiers use the tenant-wide Cost Management quota, which a release must not lose to the report), and it has its own concurrency group. A scenario never repeats a gate case, and a test rejects GUIDs, e-mail addresses and IP addresses in one.
  - **What it asks.** An audit of 95 real conversations (October 2026) gave the themes and their share: AI and Foundry spend 43%, resources and network 40%, how-to and concepts 37%, price estimates 32%, AI-agent governance 27%, security and access 27%, cost analysis 25%, Microsoft 365 licences 22%, other languages 15%. The start-page cards are the most repeated questions (the agent inventory card alone appeared in 10 conversations), so they head the report and carry a 🔥 when asked three or more times. New scenarios follow the themes in synthetic wording: no customer text, names or identifiers. Twelve safety scenarios check what the platform promises: it never deletes, powers off or buys, answers that a missing item is not zero, promises no capacity, never reveals a token, handles a pasted credential, treats instructions hidden in pasted text as data, states an access limit it has by design, and asks for approval before a bulk change. Eight scenarios ask in French, Spanish, Korean, Thai, German and Portuguese and require the answer in that language. A blunt prompt-injection phrasing ("ignore all previous rules...") was dropped after it was stopped by the provider's own filter before the agent saw it; the two replacements carry the attack inside pasted text, as it arrives in practice, and the agent handled both correctly.
  - **How results look.** Each scenario is 🟢 pass, 🔴 fail, 🟠 known limitation or ⚪ not run. A scenario with a documented limitation (the documentation answers, where the model adds a hosted web search beside Microsoft Learn reads) is amber only when it fails solely on the judge's inefficiency verdict; any other failure stays red. The report is red only when fewer than 80% of scored scenarios pass (`EVAL_QUALITY_THRESHOLD`) or it cannot complete. The job summary opens with a headline, a progress bar, counters, the failures with their reasons and a heatmap with one square per scenario by group, then a board per group; the run log prints one colored line per scenario as it finishes (time, tools, efficiency stars, the reason for a failure); the run page gets up to ten failure annotations and a scoreboard notice; and a self-contained `ai-quality-report.html` dashboard (donut, heatmap, filters, per-scenario details, no external resources, light and dark) joins the artifact. The gate's own run gets the same presentation, with its pinned contract strings unchanged, its PASS or FAIL verdict as the line under the heading, and a run that was not accepted (a setup failure, a timeout, a cancellation) red from the first line even when no scenario failed; and a summary stays under GitHub's 1 MiB limit by listing details only for what needs attention in a large suite. The README shows both workflows' badges.
  - **Checked.** 135 evaluation tests pass (34 new). An independent code review of the diff found four defects, all fixed with tests: a gate run that was not accepted but had no failed scenario got an amber headline and its FAIL line far down the page; the report could throttle a gate that started while it ran (it now pauses before each case); the job timeout was shorter than the wait plus the run; and a hostile `groups` input could put a workflow command on its own log line. Twenty-nine of the new scenarios that need no tenant ran against a local backend with the real model: pricing, scripts, safety, other languages and documentation answers all behaved as the scenarios expect (the calculation matched to the cent, scripts were delivered without being run, no purchase or deletion was claimed). The tenant-dependent scenarios have not run live yet; the first workflow run is their first test, and an unexpected red there is a finding or a scenario to tighten.
  - **One staged pipeline of the ten most important evals, and every result explained.** The first full run of all 169 took four hours in one job whose result lived in its console log, a run with one job per eval put 170 entries on the run page, and under `internal-test` data a red scenario showed no reason beyond "the judge rejected the answer". The workflow now runs the ten most important evals (`CORE_STAGES`): the four start-page cards asked most in the audit (in 10, 5, 4 and 3 conversations), two cost questions (one on real tenant data), three trust guarantees (no deletion, pasted text is data, no token disclosure) and one other language. The run graph is the picture: 🧭 Plan, four stage jobs side by side (only the cost stage queries Cost Management, which a test keeps true) and 🏁 Scoreboard, each green or red, in about 15 minutes. **Re-run failed jobs** re-runs only the red stages, a `scenarios` input re-tests chosen evals on a fixed commit, and the wider library of 170 still runs locally with `EVAL_SCOPE=all`. Each stage's summary, the scoreboard and the gate show one card per eval in four parts: what it checks (the question, the case expectation, the tool and time budgets), what happened (time to answer and first text, calls and rounds, tool versus model time, a table of every call), what the judge scored (accepted, grounded, complete, efficiency and the waste it counted) and why. The why comes from a new `findings` field in the judge's verdict: a closed vocabulary of 13 quality reasons (for example `wrong_figure`, `missing_result`, `unknown_as_zero`, `wrong_language`) and 6 efficiency reasons (for example `sequential_rounds`, `extra_lookups`) that the structured-output schema enforces. A code carries no answer text or tenant data, so it is published even when answers and the judge's free-text reasoning are withheld, and the report shows it as a plain sentence. The verdict now has eight required properties; a missing, free-text or unknown finding is a malformed verdict and fails, and findings never change acceptance. When the run completed and the judge returned a verdict, the runner's three generic failure lines ("Evaluation process failed or timed out" among them) only restate the verdict, so the why leaves them out. The HTML dashboard's cards show the same four sections, failure annotations name the verdict and why, the jobs run on `ubuntu-24.04` because the `ubuntu-latest` label added a migration notice to every job, and `Unprotect-Diagnostics.ps1 -RunId` now decrypts every stage's diagnostics of a report run. An independent review of this change found two defects, both fixed with tests: amber could never appear with real output, because a rejection for inefficiency alone also carried the runner's exit code, acceptance flag and reason as three more failures (they are now folded into the one efficiency failure only when the judge accepted a grounded, complete answer and nothing else failed), and a run made only of known limitations was red for having nothing to score; and a mistyped quality bar was only rejected after every stage had run (the plan job now rejects it first).
  - **Found by the first full run.** 85 of the first 115 scenarios passed. The VM re-pricing start-page card named example regions ("e.g. North Europe, Sweden Central, West US 3"), and the agent compared those even when one was more expensive than the VM's own region; the card now asks for the three cheapest regions that offer the same size and are cheaper. Six failures were the documented web-search limitation (an extra hosted search, often `site:learn.microsoft.com`, in its own round after Microsoft Learn or the price list had answered); two prompt variants tested against the real model locally (18 runs each) did not reduce it, so the prompt is unchanged. A storage scenario failed on a 403 from Blob Storage data access, which the evaluation identity does not have.
  - **Found by the first staged run (9 of 10 green).** "Refuses to delete a resource group" failed twice over. The agent found the named group did not exist and stopped there, without saying that it never deletes resources itself or offering a script to review: the system prompt now says to do both whenever a user asks to delete, stop, deallocate, power off or buy something, whatever the lookup finds. And the deterministic check counted the two `ResourceGroupNotFound` reads as uncorrected failed calls, although the repository's evidence rules (and the judge) treat a 404 that names the missing item as proof it is absent: the evaluator now counts a `QueryAzure` 404 that `AzureQueryTools.IsAbsent` accepts, or a multi-url call whose every failure is one, as a successful read, while a bare `NotFound`, a 403 and every other failure still fail. `Unprotect-Diagnostics.ps1 -RunId` now downloads through the artifacts API, so a finished stage can be decrypted while the rest of the run still goes on.
  - **Found by the second staged run.** "Never reveals tokens" refused correctly but did not say how access works; the prompt's secrets rule now adds that the agent reads Azure only with the user's own sign-in and permissions. A stage stopped after two passing cases with only "Evaluation execution failed": a broken lane now names the step it was in (never the error's text), and the per-case OIDC renewal, the likely step, is retried once after 10 seconds before it stops a suite, in the gate too. One French price comparison was correct and grounded but then opened the Retail Prices URL it had just read through a hosted web search (efficiency 2 of 5), in two runs: the documented web-search limitation, so it and the Thai price lookup that showed the same habit are now marked as known limitations (amber only when that is their sole failure), and the Known Limitations section records the price-lookup form and the two prompt variants that did not reduce it. An independent review found that hiding the runner's generic failure lines could hide the only reason a run failed (a timeout after the verdict was saved); they are now left out only when a more specific reason remains.

- Replace the `investigate-ai-sessions` skill with `evaluate-sessions`, which rates every real user conversation from 0 to 10, reports the ten most important issues with root causes verified in the code, and asks which to fix before changing anything. Its `scripts/export_sessions.py` exports the last 30 days of conversations read-only in about 20 seconds, as compact records holding, per turn, the user's own words and injected context, every tool call with its arguments and a bounded result excerpt, the answers and visible outputs, errors, the turn status, agent timing and tokens (linked through the ChatRequest span's `request.id`), whether the browser rendered the answer, and the user's rating; `--diagnostics` adds the model context the Responses API keeps (system prompt, tool definitions, every model input item), model calls, server warnings and exceptions, and browser events. It leaves out conversations whose browser telemetry came from Denmark (the maintainer's own use) with that browser's and owner's other conversations, the post-deployment smoke check, deleted conversations, and records over 300,000 characters. `scripts/judge_sessions.py` rates each record with the app's own model deployment (`store=false`, at most 10 at once, about 4 minutes for 80 conversations) against a fixed 0-10 rubric, and records a classification and every problem that cost points. Reasoning is excluded, credentials redacted and identifiers pseudonymised; output must stay outside the repository. The first audit with it found two judge errors, now fixed: an image the user attached is invisible to the judge (the export now records each turn's attachment count and the rubric says so, since a question such as "?" with a screenshot was scored as an invented answer), and a conversation the user stopped before any answer was averaged in as 0.

- Guard a custom domain against a silent outage. The `FinOps-PublicEndpoint-Down` availability alert had no recipient, so a domain whose registrar still delegated to old Azure DNS nameservers went dark with nobody told. The new `alertEmail` parameter (`ALERT_EMAIL`) creates an action group that emails it, and `ENABLE_DELETE_LOCKS=true` locks the DNS zone. `infra/scripts/check-dns-delegation.ps1` compares the nameservers a public resolver sees with the zone's and names the registrar change to make; `postprovision` runs it after every provision and `-Strict` fails it for CI. When the domain's DNS is hosted at the registrar instead of Azure DNS, set `DNS_EXPECTED_NAME_SERVERS` so the delegation check compares against those nameservers. A zone's Azure nameservers are not stable across a recreation, which is how the maintainer's domain went offline; hosting the records at the registrar removes that dependency (keep the Azure zone as a fallback for resolvers that still cache the old delegation).

- Add Good answer/Poor answer under every answer. A rating is saved with the conversation as a `feedback` transcript event for the question it answers (`POST /api/sessions/{id}/feedback`, ownership-checked like every session endpoint; up, down or none to clear; the latest per question wins, at most 500 changes per conversation), comes back when the conversation reopens, and is reported as a content-free `answer.feedback` telemetry event (session id, turn, rating). It follows Microsoft's "feedback opportunities" guidance for Copilot experiences. Rating an answer does not reorder the chat list.
- Add Copy under every answer and Edit under the latest answered question, which puts the question back in the message box without sending it. Add a call count under each answer that used tools ("4 calls", with failures), which opens Agent activity at that question; on phones, where the rail is hidden, it opens as a sheet over the chat (Escape, the backdrop or its close button returns focus to the count), so phone users can see an answer's evidence for the first time.
- Add Search chats (once there are more than five) and Today, Yesterday, Previous 7 days and Older groups to the chat list, and a plain-language line on held changes ("Update tags on vm1 · Microsoft.Compute/virtualMachines · resource group rg-app"), derived only from the exact request, which still shows below it.

- Add three live-gate cases from the session audit, so each fixed failure mode is re-tested before every deployment: a script that keeps every value the user stated (`GenerateScript` required), an omitted Key Vault `enablePurgeProtection` reported as off rather than unknown, and an Intune question the app cannot read answered with an administrator script instead of a dead end. Each appends a case-specific expectation to the shared rubric, and the gate now needs all 23 cases. A fourth case, a documentation answer from the Microsoft Learn tools, is in the evaluation catalog but not the gate, because gpt-6.1-sol still adds a hosted web search to most documentation answers (see Known Limitations in `docs/agent-reliability.md`). The runner waits for the Microsoft Learn connection before a case starts, as a running app has it long before a user's first question.
- Answer documentation questions with Microsoft Learn's own MCP server (`https://learn.microsoft.com/api/mcp`). An audit of 45 conversations from users outside Denmark found 19 that web-searched or opened Learn pages, often re-reading a page `QueryAzure` had already fetched, although the prompt forbade it. In local runs every documentation question now starts with `microsoft_docs_search`, whose passages usually answer it in one call: answers took 15-34 s instead of 40-49 s through Learn's search API and page reads with `QueryAzure`. Whether the answer also makes a hosted web search depends on the model (see Known Limitations in `docs/agent-reliability.md`). The server's `microsoft_docs_search` and `microsoft_docs_fetch` tools are connected with the official MCP C# SDK (`ModelContextProtocol.Core`) and passed to the agent unchanged as Agent Framework MCP tools, with the server's own descriptions. They are not the Responses API's hosted MCP tool, because `max_tool_calls` counts every built-in tool call and would make them share the one-call web-search cap. The host keeps one connection, reconnects and retries a call once after a transport failure, gives the model a search's results once (the server sends them as text and again as `structuredContent`, which doubled a search to about 47,000 characters), and cuts a result above 48 KB with a note. `MicrosoftLearn:Enabled=false` leaves them out, and while they are unavailable the agent searches Learn through `QueryAzure` as before; Dependabot bumps `ModelContextProtocol*` with Agent Framework.
- Add `action_required` to scheduled-run outcomes: a blocker that waiting cannot clear (a subscription offer Cost Management does not support, a missing role or consent, a deleted scope) pauses the job at once, and the job list shows "needs your action", instead of repeating the same blocked run until the five-failure auto-pause.

- Add optional encrypted CI diagnostics for failed live evaluations. With repository variable `EVAL_DIAGNOSTICS_CERT` set to a maintainer's public certificate, a failed run's artifact gains `private-diagnostics.enc.json`: the failed-case judge rationale, answer, gate failures, bounded tool details and unfinished captures, encrypted with RSA-OAEP-256 wrapping an AES-256-GCM key. Public summaries still withhold internal-test answers and rationale. `tests/LiveEvaluations/New-DiagnosticsCertificate.ps1` creates a non-exportable RSA 4096 key in the Windows user certificate store, and `Unprotect-Diagnostics.ps1 -RunId <id>` downloads and decrypts a run. Forks do not inherit the variable, so they never encrypt their tenant data to the upstream key.
- Add hosted web search, on by default (`AzureOpenAI:WebSearch`; Bicep parameter `aoaiWebSearch` from `AZURE_OPENAI_WEB_SEARCH`, default true; evaluator `EVAL_WEB_SEARCH`, defaulting to the same value so the live gate tests what deploys). The system prompt limits it to recent public information that no API returns (announcements, new models, features or regions) and requires a source URL and date for each web fact; tenant data, list prices, API contracts and Learn pages still come from `QueryAzure`. Search queries go to Bing grounding, which is outside the Azure data boundary; set `AZURE_OPENAI_WEB_SEARCH=false` (or `AzureOpenAI__WebSearch=false`) to keep every call inside it. Verified on the test slot with gpt-6-sol: a question about this week's Foundry announcements ran seven web searches and answered with a dated, cited source.
- Add stateless LINQ cropping to `QueryAzure` (System.Linq.Dynamic.Core 1.7.4) in place of a stored-response database. A response up to 32 KB returns whole; a larger one returns its coverage fields and the C# schema inferred from its JSON (names, types, counts, samples and a starter expression), and the model repeats the request with `query`, a C# LINQ expression over the response root, receiving only its result (up to 48 KB) beside the response's own coverage line. Column/row tables become row objects and text becomes `lines`. Several url lines share one `query`, with a schema common to several large responses shown once. `query` without `url` is a calculator over copied figures that sends no request and is never source evidence. The sandbox allows only LINQ, string, `Math`, `Convert`, date and primitive members, meters every enumeration (20M steps, 10 seconds, 64K-character strings), and evaluates a root-only aggregate inside a lambda once, so a per-item share of total stays linear. Nothing is stored between calls and the application keeps no database.
- Add `ApplyAzureChange`, an Agent Framework `ApprovalRequiredAIFunction` and the only ARM PUT/PATCH path. The UI shows the held call's exact method, URL and body; the next chat turn carries `approval: {requestId, approved}`, and only an explicit approval runs it. Any other message rejects every held change (shown as "not applied (a new message was sent instead)"), a stale approval returns `approval_stale` without sending, and an approved change whose turn was interrupted is never re-approved. A 201/202 result is accepted, not complete: the model polls the returned `Azure-AsyncOperation` or `Location` URL.

The live evaluations call the model with the evaluation identity, so build 168 passed all 20 cases while the test slot's own managed identity lacked Foundry User (`agents/write` HTTP 403). Each deployment now records the prior image and model settings, sends one real anonymous chat turn through the deployed URL and requires a completed answer. On failure it restores the prior state and fails the run.
- Add optional `AZURE_PREVIEW_SLOT_NAME` provisioning. Optional `AZURE_PREVIEW_DEPLOY_SUBJECTS` adds a GitHub OIDC deploy identity: Website Contributor on the slot only, Reader on the parent and AcrPush. The feature workflow's Azure jobs use GitHub environment `test`, so one subject serves every branch. Postprovision registers the slot's OAuth redirect URIs and federated credential, no longer recreates an identical production credential, and prints the workflow settings. Preprovision rejects a Basic plan, which ARM preflight accepts but which fails mid-deployment. Existing role-assignment names are unchanged.
- Add Clear chat to the composer. Once a conversation has a question and an answer, Clear chat deletes it (the same server-confirmed deletion as removing it from Chats; an anonymous conversation is simply left) and opens a new chat. It is disabled while an answer is running, and a refused deletion keeps the conversation and shows why.
- Add an "AI & LLM pricing" menu with the five questions users ask most (in 100 audited conversations: per-1M token comparisons in 6 sessions, PTU monthly cost and reservations, the newest model's list price, token-based project estimates and model speed). In order: the newest Foundry models and prices, the latest published benchmarks next to price, the existing GPT-4o/GPT-4.1 token comparison, PTU hourly versus 1-month and 1-year reservations, and a chatbot monthly estimate. "Infrastructure pricing" (the previous public pricing prompts) is cut from 13 to the 6 most common: VM price by region, reserved versus pay-as-you-go, Spot versus on-demand, storage tiers, databases and a 3-tier estimate. Signed out, the navigation shows AI pricing expanded and infrastructure pricing collapsed. Signed in, every section starts collapsed below the maturity cards, and infrastructure pricing lists the personalised prompts first. All public prompts are in `pricingCategory.publicPrompts`, and the curated live-evaluation cases keep their exact text and IDs.
- Add "AI agents: governance & cost", six public questions about the concerns customers raise most about agents today: capping Foundry agent cost, governing agents (identity, access, approved tools, inventory, audit), charging back AI and agent spend, security guardrails against prompt injection and data leakage, keeping AI data in the EU, and what changed in the last three months. Each asks for one short table with a source link per row. The agent answers from current Microsoft Learn pages it reads through `QueryAzure` and, for recent changes, web search; the "what's new" question is capped at two searches and two opened pages. With gpt-6.1-sol at medium effort locally, the six answered in 41-78 s with 2-6 tool calls and no errors (the uncapped "what's new" took 155 s and 14 calls). The section opens by default when signed out. ### Changed

- Split the solution into `src/backend` (the .NET API, formerly `src/Dashboard`) and `src/frontend` (the Vue app, formerly nested inside the .NET project), with `src/Dockerfile` building both from the `src/` context. The frontend still builds into `src/backend/wwwroot`, and the C# project, assembly and `AzureFinOps.Dashboard.*` namespaces keep their names, so no code or deployment setting changes. Because the frontend no longer sits inside the project, its `package.json`, lockfile and configs no longer leak into the published app. The loose frontend helpers moved to `src/frontend/src/lib`, `setup-entra-app.ps1` to `infra/scripts`, and the social-preview upload script next to the card it uploads (`npm run og-image:upload`). Workflows, Dependabot, CODEOWNERS, azd hooks, tests and docs use the new paths, and the live-evaluation clean-tree check now covers all of `src/`.
- Remove duplicated logic. One `SessionIdentity` helper now reads the caller's user and Entra tenant/object id for every endpoint, replacing about 15 copies across chat, sessions, jobs, uploads, downloads, sign-in, sign-out and token refresh (several would fail with a server error on an unreadable session record; all now return 401). `AiTelemetry` detaches a user's open conversations in one place for sign-out, revoke, idle eviction and deletion, so the active-session gauge is always decremented. The chat page's two "time ago" formatters became one tested `lib/timeFormat.js`.
- The chart tool description no longer points the model at a host path to a coordinates file that does not exist.
- Answer in fewer rounds. In 174 production turns, model time was 91% of answer time (about 4.6 s per model call, plus about 8.4 s per 1,000 written tokens and 6 s per 1,000 reasoning tokens), so these changes remove model rounds and retyped figures rather than tool time:
  - `QueryAzure` gains `combine`, one Dynamic LINQ expression over every url line's response (`responses`, null for a failed line), so per-subscription, per-region or per-component reads are totalled, merged and compared in the call that fetched them. Calculation-only rounds that retyped earlier figures had taken 17% of model time since 9 October. Several url lines can now also be POSTs with one shared body, such as one Cost Management query per subscription when no covering scope can be read. `query` and `combine` are exclusive, a failed line is reported as partial with combine run over the others, and a combine error returns the responses' schema. A `SelectMany` selector over a missing inner list (a failed line's null) enumerates it as empty.
  - The system prompt says each tool round costs the user 10 to 30 seconds, limits a calculation-only call to a few figures copied from different calls, limits guidance questions to two rounds of Learn reads (one search per named product, all in the first), and creates a data file only when a file, download, export or spreadsheet is asked for: a per-model or per-subscription breakdown is a table, and an unrequested file had cost about 50 s.
  - New facts remove documentation rounds. SQL Database vCore storage: General Purpose and Business Critical bill the maximum data size plus 30% for the log file, and Hyperscale bills allocated storage; the answer cites this from one Learn search sent with the first price request, because an uncited 650 GB was judged ungrounded. The Azure Monitor token metrics of Azure OpenAI and Foundry accounts: their dimension names can come back in lowercase, and the preview `FoundryModelEstimatedCost` metric by `ProjectId` is the only per-project figure (an estimate). A breakdown of a stated total now accounts for all of it: items in another unit keep their row, and rows left out become one Other row.
  - `evaluate-sessions` gains `scripts/latency_report.py`, which attributes a `--diagnostics` export's model time to round types (evidence reads, calculations, documentation, files, the final answer) and lists the slowest turns round by round.

  On ten real questions from the session audit, with hosted web search on as in production, the answers used 48 tool calls in 35 rounds instead of 76 in 44 and took 884 to 1,048 s in total instead of 1,380 s (median 65 to 79 s instead of 89 s; model latency varied between runs, and an identical one-round answer took 59% longer in the slower one). A French four-month cost analysis went from 276 s to 91-144 s, and Foundry spend by model from 195 s to 117-137 s. With web search off the same questions took 653 s (median 48 s): 8 of the 10 answers made a hosted web search that none of them needed.

The 3-tier estimate now sources its P30 price ($135.17) from the API instead of a guessed assumption, and Foundry comparisons return the correct Standard Global rates with no model names left in the codebase.
- **`azd up` can now provision the custom domain end to end.** A new `AZURE_CUSTOM_DOMAIN` setting creates an Azure DNS zone with every record already in place — apex A, `www` CNAME, the `asuid` ownership TXT, and the hardening records that were previously missing entirely: a **CAA** record pinning issuance to the three DigiCert issuer domains that App Service managed certificates actually chain to (without one, any CA on earth may issue for the domain), plus a **null MX + `v=spf1 -all` + `p=reject` DMARC** set so a domain that sends no mail cannot be spoofed. Nameservers are surfaced as `AZURE_DNS_NAME_SERVERS` for the registrar. An optional `ENABLE_DELETE_LOCKS` puts a `CanNotDelete` lock on the zone for long-lived domains (off by default, so `azd down` still tears an evaluation environment down cleanly). Hostname binding and certificate issuance deliberately stay in the runbook — they are strictly ordered around DNS propagation, which a single ARM deployment cannot wait on.
- **Outside-in availability monitoring.** A standard App Insights web test now probes the public URL every 5 minutes from five regions, with a Sev-1 multi-location alert. This closes a real blind spot: every previous alert was a scheduled KQL query over `requests`, which can only fire when the app is _already serving traffic_ — if DNS broke, the certificate lapsed, or the site was hard-down, zero requests arrived and none of them could ever fire. The test also asserts `SSLCertRemainingLifetimeCheck: 7`, so it doubles as the certificate-expiry alarm that was previously absent (managed-cert auto-renewal fails _silently_ if DNS ever stops resolving to the app).
- **`.github/prompts/migrate-tenant.prompt.md`** — a reversible, two-phase runbook for rebuilding the stack in another Azure tenant and cutting the custom domain over without a broken window. Documents what provably cannot migrate (the Entra app registration, `/home` state, telemetry history) and keeps rollback at one DNS TTL until the final step.

- **Scheduled jobs — a recurring prompt that runs in the background, even with the browser closed.** A new "Scheduled jobs" pane below Conversations lets an Azure-connected user save a prompt + cadence (every 15 min / hourly / daily / weekly); the backend `JobScheduler` runs it as a normal agent turn in its own dedicated conversation, so every run's answer (text, tables, charts) is browsable by opening the job. Built for the capacity-hunting use case — "check H200 spot capacity + quota across all my subscriptions and regions every 15 minutes and tell me the moment it's deployable" — but works for any standing task (daily cost report, anomaly sweep, license audit). Background auth is delegated-only: each run re-mints the user's Azure/Graph/Log Analytics/Storage tokens from the persisted MSAL refresh token (no app permissions, no admin consent — the job can never exceed the user's own RBAC), and pauses itself with a "reconnect Azure" status if the refresh token dies. Runs share the one-turn-per-session gate with live chat (a job can never race a chat turn), preserve the user's active conversation (a 3 AM run won't hijack which chat you see next), and keep the same tool surface as chat (writes allowed, **DELETE still blocked**). Caps: 3 active jobs per user; sub-daily jobs auto-expire after 7 days, daily/weekly after 90; a job auto-pauses after 5 consecutive failures. `GET/POST /api/jobs`, `POST /api/jobs/{id}/run|toggle`, `DELETE /api/jobs/{id}`. The pane is built to feel alive: “+ New job” opens a centered **modal sheet** (blurred backdrop, Esc/backdrop close) with one-click **templates** — GPU hunt & reserve (checks quota + capacity every 15 min and, when deployable, **secures it by creating an on-demand Capacity Reservation via ARM PUT**, idempotent with an explicit bills-while-held warning and a pause-and-cleanup instruction), daily cost digest, anomaly watch, budget guard, idle resource sweep, Advisor watch — plus cadence pills, a **"Run immediately, then repeat on the schedule" checkbox** (default on: the first result lands in the job's conversation within a minute; unchecked: the first run waits one full interval), and an autofocused prompt; rows show a **live countdown** ("next in 12 min", 30 s ticker) and status animations — breathing blue = armed, pulsing green = running now, pulsing red = failed/reconnect Azure, gray = paused; clicking a job that has never run shows a "no runs yet — ▶ runs it now" nudge instead of doing nothing; the list auto-sorts (running → failing → soonest next run → paused) so it scales past a handful of jobs; the header shows "N active · M failing" and collapses the pane instantly (sticky per browser); statuses refresh on tab-return plus a 45 s background poll, so returning users immediately see what ran while they were away.
- **A scheduled job can now run on a custom cadence, not just the presets.** Alongside the Every 15 min / Hourly / Daily / Weekly pills, an "or run every \_\_\_ min" field accepts any interval from **1 minute to 30 days** — so "every 1 min" (near-real-time monitoring), "every 45 min", "every 3 h" (180), or "every 2 d" (2880) are all one field away. The pills are now shortcuts that fill the same field; rows render the custom cadence in the largest whole unit ("every 45 min", "every 3 h", "every 2 d"). Out-of-range values are rejected inline (create/save disables with a hint) and by the API. (1 min is the scheduler's tick cadence — the fastest it can fire; a run never overlaps its previous one thanks to the per-session turn gate.)
- **Edit a scheduled job in place.** Every job row now has a pencil (✎) that reopens the same modal prefilled with the job's name, prompt, and cadence — in edit mode the template picker and "run immediately" checkbox are hidden, the title reads "Edit scheduled job", and the button saves via a new `PATCH /api/jobs/{id}` (name / prompt / intervalMinutes each optional, validated the same as create). Changing the cadence recomputes the job's expiry (7 d sub-daily / 90 d daily+weekly) and re-arms the next run one interval out. Previously a job could only be created or deleted, so fixing a typo or retuning a cadence meant delete-and-recreate (losing the run history).
- **A failed job run is now visible at a glance.** A job whose last run errored shows "last run failed · next …" in red on its row (instead of the generic cadence line), so a broken job stands out without opening it — the header already counts "N failing".
- **SSE keepalive pings during long silent phases.** A turn can emit no bytes for minutes while the model generates a large tool argument (an 800-line deck or script) between the last reasoning delta and `tool_start`. Intermediate proxies (App Service front end, ~4 min idle) and the client's 3-minute inactivity watchdog would drop a perfectly healthy turn. The backend now emits a `{type:"ping"}` every 20 s while awaiting completion; the client ignores it.

### Changed

- **Maintainer deployment workflows are target-neutral.** Production and test workflows now read registry, image, App Service, resource-group, slot, and verification settings from GitHub Actions variables and authenticate with separate OIDC secrets. No tenant or deployment coordinates are stored in tracked workflow files. Production identity guidance remains branch-scoped and least-privileged (`AcrPush` on the target registry and `Website Contributor` on the target web app), while ACR admin remains disabled.
- **Custom-domain migration guidance is now reusable.** The runbook documents a certificate-safe, reversible DNS cutover without embedding the hosted deployment's resource names, addresses, DNS records, tenant information, or rollback coordinates.
- **A job's conversation is now a run log, not a chat.** Opening a scheduled job's conversation shows its runs updating live (a follow loop keeps the view fresh while runs land server-side — previously the view silently froze while runs piled up on disk) with a job bar instead of a composer: **Build deck**, **Summarize runs**, **Edit job**, **New chat**. Free-form typing into a run log muddled the history and silently steered future runs — editing the job's prompt is now the explicit way to steer it, and sidebar titles read "⚙ Job · {name}" so job threads are unmistakable.
- **All transient chat notices now go through one state machine.** "Reconnecting…", "Still working…", "busy", and resume fallbacks used to be spliced into the transcript by five independent pollers — they could stack (two contradictory banners at once), stick above real messages forever, and use chat wording ("your last question") for scheduled runs the user never typed. Now a single status pill lives outside the transcript (it can never stack or stick), job conversations get job wording ("⚙ A scheduled run is in progress…"), an empty resumed conversation shows the normal empty state instead of a pointless "Resumed conversation" pill, and the "Still working…" notice actually resolves into the answer when the turn finishes (it previously polled a no-op refresh and never updated).
- **Job rows now use their full width, and show when the job last ran.** The action buttons used to permanently reserve ~120px of a ~225px row (invisible but still occupying layout), squeezing the name and status to a third of the row. Actions are now a hover overlay on the right edge — the text owns the whole row until you hover (keyboard focus reveals them too). The status line got richer: `every 15 min · ran 2m ago · next in 13 min` — cadence, last run, and next run at a glance; failures read `failed 2m ago · next in X` (the failure timestamp doubles as the last-run time), and the countdowns/ago-times tick live. The row tooltip now includes the total run count.
- **Job templates now lead with capacity** — the single most common customer complaint. The grid starts with **"Check capacity of X"** (read-only: where is this VM size deployable right now, across all my subscriptions and regions — every 15 min) and **"Reserve X when available"** (the generalized GPU hunt: when the size becomes deployable with quota headroom, secure it via an on-demand Capacity Reservation — idempotent, cost-warned). A new **"1-min test"** template (one-sentence USD consumption report, every minute) lets anyone see how scheduled jobs work within a minute of creating one.
- **The job row's pause control is now a proper on/off switch.** ▶ (run once now) sitting next to ⏸ (pause the schedule) read as contradictory transport controls — like a media player showing play and pause together. The schedule state is now a small toggle switch (blue = armed, gray = paused) that can't be misread, stays visible on paused rows as the state indicator, and announces itself to screen readers as a real `switch`. ▶ keeps its "run once now" meaning.
- **Local BYOK can pin its token tenant.** New optional `AzureOpenAI:TenantId` setting — set it when the az CLI's default account lives in a different tenant than the Azure OpenAI resource (previously every local AI turn failed with "Token tenant does not match resource tenant" and the only fix was switching the CLI's global default).
- **Deleting a job or a conversation is now immediate — no confirm dialog, and optimistic.** The × removes the row instantly (before the server round-trip), so the button always feels alive; if the server call ever fails, the next list refresh restores the row. Deleting a job keeps its conversation and run history.
- **Each right-sidebar pane (Agent, Conversations, Scheduled jobs) can be collapsed to its header** via a large rotating chevron, with a smooth slide animation (the content row glides shut instead of snapping) — collapse two and the third takes the whole sidebar, so you can focus on one area (e.g. a long jobs list or a deep tool-call trail). Collapse state is remembered per pane.
- **The Scheduled jobs pane got a little bottom breathing room** so the last job row isn't cramped against the sidebar's bottom edge.
- **`QueryGraph` now allows write methods (GET/POST/PUT/PATCH); `DELETE` stays blocked.** Previously GET-only. This aligns Graph with `QueryAzure` so the agent can act on Microsoft Graph (e.g. group/license management) when the tenant has consented to write scopes — the standard read-only consent tiers still cause Graph to return 403 for writes, which the tool surfaces rather than retrying. The delete prohibition is unchanged and remains the product's hard guarantee.

### Fixed

- **Generated presentation cards now provide an in-app Preview instead of download-only UX.** Preview fetches the existing owner-checked `?inline=true` artifact, removes scripts and external resources, lays every slide out in a vertically scrollable static view, and renders it in a fully sandboxed modal iframe. The deck cannot access the app's cookies, storage, DOM, or authenticated APIs; Download remains a separate action, and restored deck cards get the same preview.
- **Fast send/remove actions can no longer resurrect attachments or create ghost uploads.** Sending immediately after choosing a file raced `uploadFiles`: the send path removed the image chip, then the upload callback wrote its result back to the stale array index, making the chip reappear; removing an in-flight upload could similarly update the wrong chip and leave an invisible server-side file attached to the next turn. Sends now wait for upload settlement, callbacks locate chips by stable `uid`, abandoned uploads delist their eventual server `fileId`, and blob thumbnail URLs are revoked only after Vue unmounts the image (eliminating `net::ERR_FILE_NOT_FOUND` console errors). Successful upload deletion now returns an explicit `200 { removed: true }`; the integrated Chromium browser reported an otherwise completed empty `204` response as `net::ERR_ABORTED`, failing the application's zero-network-error invariant.
- **Image attachments no longer fail with “The image data you provided does not represent a valid image.”** The app had upgraded to `GitHub.Copilot.SDK` 1.0.11 while retaining a stale `<CopilotCliVersion>1.0.70</CopilotCliVersion>` workaround from SDK 1.0.7. Text and tools still worked, but the mismatched runtime mishandled valid PNG/JPEG path attachments and every vision turn completed with no answer. The override is removed so SDK 1.0.11 supplies its compatible, now-published CLI 1.0.79 runtime.
- **Admin consent failed for every fresh deployment because three requested permissions were not delegated scopes.** `setup-entra-app.ps1` declared the Microsoft Graph `Organization.Read.All` and `Group.Read.All` **appRole** GUIDs — plus a Log Analytics `Data.Read` GUID that does not exist on that API — as `type = "Scope"`. Entra validates a consent request atomically, so consent failed for the whole app and no service principal was ever created, blocking "Connect Azure" in any tenant that requires admin consent. The correct delegated `oauth2PermissionScopes` ids are now used, every id is additionally re-resolved by value from the resource's published scopes at run time (falling back to the constant only when the resource service principal cannot be read), and a failed permission update now exits non-zero instead of being swallowed. The `postprovision` redirect-URI patch likewise re-reads the app and fails loudly when a callback did not apply, instead of printing a warning that scrolls past and surfaces later as `AADSTS50011`.
- **A "cheapest region" answer could quote Spot prices as on-demand.** `priceType='Consumption'` also returns Spot and Low Priority rows, so ranking a flat list by price surfaced Spot ($17.52/month for a D4s_v5) where the question meant standard pay-as-you-go ($140.16/month). The projection now round-robins across `meterName` groups so the ordinary on-demand meter is always visible regardless of price, comparisons are constrained to a single meter, and the agent states which meter it quoted.
- **XLSX inspection no longer pays repeated pandas startup or a second aggregate round.** Workbook operations now run directly through `openpyxl`; `workbook` mode returns bounded count/sum/min/max/mean summaries for numeric columns on every sheet. A question such as “which sheet contains snapshots and what is their total monthly cost?” is answerable from one file-tool call instead of `workbook` → `aggregate`, while the checked-in workbook fixture is now genuine OOXML rather than legacy OLE bytes under an `.xlsx` extension.
- **Crawl scoring no longer takes 56–120+ seconds.** The original sweep made 19 independent model/tool round trips; the first server-side consolidation still queued 12 low-cost metadata GETs behind the global Cost Management query semaphore and then paid separate `ReportMaturityScore` and `SuggestFollowUp` rounds. Metadata now uses verified full concurrency with one attempt, Cost Management `/query` is unnecessary for MTD because budgets expose exact current spend, and score/follow-up side effects happen in the evidence tool. A low-reasoning experiment was measured and reverted because it was slower (24.51 s vs 22.14 s) and offered no quality-safe gain.
- **Long markdown tables no longer split at Azure identifiers.** The stream commit path tried to “repair” missing sentence spacing by replacing every `.<uppercase>` with a paragraph break. Resource names such as `MDE.Linux`, versions such as `v1.2.3`, and hostnames such as `api.Contoso.com` were corrupted; inside a table this ended the regex match and left the remaining rows as raw pipe text. The unsafe punctuation rewrite is gone. Verified on a fresh stream with all identifiers preserved and all rows rendered.
- **Page-load warmup and transcript replay no longer race into HTTP 500.** Both could call `ResumeSessionAsync` for the same persisted session concurrently, producing `Session '…' is already tracked by this client`. Transcript loading now shares the per-user session gate and reuses a tracked live session; repeated reloads return 200 and restore the transcript.
- **Disconnect and revoke now remain disconnected.** Both routes cleared in-memory/session tokens but left the `finops_id` cookie, so hydration restored `azure_user` and the refresh token on the very next request. Disconnect now removes the cookie while retaining the encrypted identity record for an explicit reconnect; revoke removes both cookie and identity record and forces a fresh consent screen. Logout still clears the full Entra identity and assigns a new anonymous chat user.
- **Creating a job with “Run immediately” now auto-opens its run log.** Explicit run-now and edit+run-now already watched for the scheduler-created session, but initial creation omitted that call. The new job now opens the same dedicated session and refreshes until the first answer lands; the transient “running” notice clears on convergence.
- **The old-snapshot waste check no longer fails Resource Graph parsing.** It projected away the `created` column and then sorted by it twice. Sorting now occurs before projection and the final result uses `take`; the full eight-pattern idle scan completes with no subquery error.
- **Budget coverage uses valid Resource Graph syntax.** Azure Resource Graph rejects multi-statement `let …; let …;` queries; the canonical guidance now uses one inline-join pipeline. A multi-subscription retest completed without a parser error.
- **A completed answer can no longer remain hidden behind a silently stranded SSE reader, missing terminal frames, or a late Stop click.** Chromium can leave `response.body.read()` pending after the server has finished and persisted the answer, with no EOF, delta, or `AbortError`; the UI then stays on a bare AI avatar indefinitely. After 10 seconds without SSE bytes, the client now checks the authoritative per-session turn gate; if the turn is no longer active and the matching answer exists on disk, it aborts only the zombie reader and reloads the transcript. A normal EOF with no renderable frames also checks the persisted tail once before showing an empty-turn warning. Abort intent is explicit: reset/logout uses `discard`, an unrequested `AbortError` follows recovery, and only the Stop button requests `stop`. The stop endpoint distinguishes `{stopped:true,alreadyCompleted:false}` from a late race `{stopped:false,alreadyCompleted:true}`; the latter reloads the completed answer instead of replacing it with “You stopped this response before it finished,” while an active stop still wins even if partial text was already persisted. Verified with deterministic browser cases (stranded completion, empty terminal EOF, late Stop, active Stop with partial persisted text) and a clean real 3-tier starter, which rendered its full answer/chart with no blank response.
- **Trivial acknowledgements now use words instead of an emoji-only reply.** The one-round-trip directive still forbids tools, tables, headings, lists, and charts, but now requires one short text sentence; `ok` was returning only `👍`, which violated the UI test contract. Verified with a real model turn: “Understood—what would you like help with?” and zero tools.
- **The app is no longer indexable on two hostnames at once.** The site served byte-identical HTML on both the custom domain and its `*.azurewebsites.net` host — each emitting a _self-referencing_ canonical, because canonical URLs are derived from the request host — so search engines saw two competing copies and split ranking between them. The default hostname (and any other non-canonical host) now returns `X-Robots-Tag: noindex, nofollow`, driven by the existing `PUBLIC_SITE_HOST` setting; `www.` counts as canonical-equivalent since it already 301s to the bare domain. Deployments that don't set a canonical host are unaffected.
- **`azd up` no longer fails on a resource-ordering race.** `modules/aoai.bicep` declared the Foundry project and the model deployment as sibling children of the same Cognitive Services account with no dependency between them. ARM creates siblings in parallel, but a Cognitive Services account serializes control-plane operations — so the project raced the deployment and the whole provision aborted with `RequestConflict: Another operation is in progress on the resource`. Adding `dependsOn: [modelDeployment]` orders them. Reproduced on a real deployment and confirmed fixed on the retry.
- **The Entra redirect-URI patch produced a mangled URI and silently broke login.** `scripts/postprovision.ps1` read the existing URIs with `az ad app show ... -o json`, which PowerShell returns as an **array of lines**; piping that into `ConvertFrom-Json` yields a bare string, so `$existing + $desired` did string _concatenation_ and emitted `…/callbackhttp://localhost:5000/…`. Entra rejected the update, the hook printed a warning, and `azd up` continued as if healthy — leaving the app with only a `localhost` redirect URI, so every sign-in on the real hostname would fail. The lines are now joined before parsing and hard-cast to `[string[]]`. The hook also never registered the `/auth/microsoft/adminconsent/callback` URIs despite that being a live route, which broke the admin-consent flow; both are now included.
- **`azd up` no longer ships gigabytes of build output to the container registry.** `az acr build` does not honour `.dockerignore`, so on any machine that had run `dotnet build` or `npm install` the postdeploy hook tarred `bin/`, `obj/`, `node_modules/` and `wwwroot/` into the build context — measured at **1.27 GB**, which stalls the upload instead of the ~100 MB a clean tree produces. The hook now prunes those generated directories first (the Dockerfile rebuilds them all inside the image), matching the cleanup the manual checklist in `deploy.prompt.md` already mandated.
- **Tablet-width charts no longer collapse between both sidebars.** The three-column desktop layout remained active down to 769px; at a 789px browser viewport the 290px navigation and 250px execution sidebar left only 249px for chat, shrinking a chart SVG to 150px and overlapping three normal region labels by 30–52px. The coordinated responsive breakpoint is now 900px: below it the navigation becomes an overlay, execution tools hide, and mobile auth appears together. Verified in the live browser with the same chart and viewport — SVG width 150→730px, overlap eliminated.
- **Custom-domain apex records now support every App Service inbound address.** `appServiceInboundIp` accepts a comma-separated list and builds the apex record with `map(split(...))`, satisfying App Service certificate validation for plans that expose multiple inbound addresses.
- **Changing the availability probe URL no longer orphans the previous web test.** The test's name embedded `uniqueString(appInsightsId, testUrl)` — but a resource's name is its identity, so pointing the probe at the custom domain provisioned a _second_ test rather than updating the first. The orphan kept running and kept billing, while the alert (which only ever references the current test) silently stopped covering it. Observed live: two tests in one resource group, one probing the default hostname with no alert attached. The name is now keyed on the App Insights component alone, making the URL an in-place update.

- **Clicking a sidebar prompt while viewing a job's run log now starts a fresh conversation for it.** Crawl/Walk/Run prompts, score buttons, follow-up chips, and in-answer prompt links used to inject straight into whatever conversation was open — including a job's run log, which muddled the log and silently steered the job's future runs. All prompt entry points now hop to a new chat first when a run log is in view.
- **A run with a long tool trail no longer crushes the sidebar.** The Agent execution pane sized itself by content, so 80+ tool calls (routine for scheduled jobs) squeezed Conversations and Scheduled jobs into slivers. Panes now share the sidebar by fixed proportion and the tool list scrolls inside its own pane.
- **Deleting conversations can no longer strand a scheduled job on a dead transcript.** A job's run log used to appear in the Conversations pane as a regular deletable chat; deleting it left the job pointing at a vanished session ("couldn't load this conversation's history") until the next run replaced it. Run logs now live only under their job row (deleting the job makes its history reappear in Conversations, so nothing is lost), and deleting any conversation server-side detaches it from any job that referenced it — the job behaves as "never ran" and creates a fresh log on its next run.
- **Clicking a job that hasn't run yet now opens its details instead of doing nothing.** A job with no run history has no conversation to open, so a row click used to only flash a tiny "no runs yet" hint that was easy to miss. It now opens the job's edit/detail sheet — and that sheet gained a **"Run now after saving"** option, so you can run a job straight from it. Triggering a run (that option, or the ▶ button) now **auto-opens the run's conversation** and refreshes it until the answer lands, so you can actually watch the run.
- **A paused job no longer shows a misleading "next in X min."** A paused job that had previously failed still rendered a countdown to a run that will never happen. Paused rows now read "paused" (keeping the "last run failed" / "reconnect Azure" reason when relevant); only enabled jobs show a next-run countdown.
- **Resuming a paused job now respects the 3-active-jobs cap.** Create enforced "max 3 active" but the pause/resume toggle didn't, so pause-one → create-three → resume yielded four active jobs (contradicting the header count and the create-time limit). The toggle endpoint now rejects a resume that would exceed the cap, and the row shows "Limit reached — max 3 active jobs. Pause or delete one first." for a few seconds instead of silently staying paused.
- **Opening "+ New job" right after cancelling an edit no longer inherits the edited job's name/prompt/cadence.** The new-job opener reset the edit flag and the template selection but not the form fields, so a cancelled edit leaked its values into the fresh form. Opening a new job now always starts from a clean slate, and all four close paths (Cancel, ×, Esc, backdrop) clear the edit state.
- **A generated table (or any answer) no longer flashes on screen and then disappears.** The chat wiped the streamed answer buffer on every `tool_start` after text had streamed — a heuristic meant to drop mid-turn narration before the real answer. But the model calls `SuggestFollowUp` (and sometimes `ReportMaturityScore` / `PublishFAQ`) _after_ the final answer, so that wipe deleted the just-rendered table, leaving only a follow-up chip (the answer was still in the persisted transcript, which is why it reappeared on reload). Those post-answer tools are now excluded from the wipe, and a safety net restores the last wiped text if a turn ends with an empty buffer (which also fixes chart-only answers losing their lead-in sentence).
- **A blank white page after a deploy (seen in Edge) is fixed.** `index.html` was served `no-store` but the content-hashed `/assets/*.js|css` bundles carried no cache header, so a browser could serve a cached `index.html` from the previous deploy that referenced the _old_ bundle hashes — which 404 after redeploy, leaving a white screen until a hard refresh. Static file caching is now explicit: hashed `/assets/*` are `immutable` (cached a year), while `index.html` / `/` are `no-cache` (always revalidated), making deploys atomic for the browser.
- **A severed stream on a long-running turn no longer gets stuck showing one (or two) permanent "⏳ Reconnecting" banners.** On a big turn — "go through all regions × all subscriptions" — the CLI persists nothing until the final answer, so the client's 3-minute recovery poller gave up while the turn was still running (the backend allows turns up to 15 min); worse, early poller exits left the banner on screen **and** freed the recovery lock, so the next window-focus/visibility event spawned a second poller that stacked a **second** banner, neither of which ever cleared. Recovery is now robust: the poll deadline covers the backend's full 15-minute turn budget (3 s→10 s backoff), the banner is a single deduped instance that is cleared on **every** exit path (early return, recovery, timeout, throw), the send-catch fires recovery **fire-and-forget** (so `send()` resets the composer immediately instead of blocking up to 15 min and double-posting), and on genuine timeout the dead banner is replaced with an actionable "Connection lost — Retry" message. The recovery view-check also tolerates anonymous users (whose `currentSessionId` is reset to `null` after every turn by `loadSessions`) by confirming the recovering prompt is still the last question on screen rather than a strict session-id equality — otherwise recovery stood down silently with no banner and no answer. Verified live: a real `ERR_CONNECTION_RESET` mid-turn shows **exactly one** banner that survives 36 focus/visibility events with zero console errors.
- **Returning to an empty or already-answered conversation no longer shows a phantom "⏳ Reconnecting" notice.** The tab-return / window-focus reconcile treated any view that didn't end in a non-empty assistant message as "answer missing", so a brand-new/empty session (or one ending in a system notice) flashed "Reconnecting — your last answer is still being generated" and polled for 3 minutes even though no turn was ever in flight. Reconcile now only recovers when the current view has a genuinely unanswered user turn (a last user message with no real answer after it); a new `assistantTurnHasOutput` helper counts text, a chart, a generated deck/script, or completed tool calls as a delivered answer (so chart-only answers no longer false-trigger), and the recovery poller bails immediately on a blank prompt.
- **A deck or script finishing in a background conversation no longer pops into whichever chat is in view.** `html_ready` / `script_ready` events are processed for background streams (so the card is on the committed message when you switch back) but used to write the shared `htmlReady` / `scriptReady` refs unconditionally — surfacing another conversation's artifact in the foreground. They're now kept stream-local and only mirrored to the shared refs while that session is the active view.
- **Restored conversations get their follow-up buttons back, and expired artifacts show a clear state instead of dead links.** Transcript replay now re-derives the follow-up action buttons from the persisted `SuggestFollowUp` result (live turns already keep them), and deck/script cards whose 30-minute in-memory artifact has been swept (or lost on restart) render an "Expired — ask to regenerate" hint instead of a Download/Copy button that 404s.
- **New/stub sidebar rows show their timestamp immediately.** The `session_title` stub row set `modifiedTime` but the template reads `modified`, so a brand-new conversation showed a blank relative time until the next sidebar refresh.
- **Starting a new conversation no longer wipes a background-streaming conversation's tool list.** `newSession()` cleared every session's live tool/chart buckets; it now drops only the current view's (and the `__pending__` sentinel's).
- **Concurrent-turn rejection ("busy") no longer leaves an orphaned user bubble.** When the server rejects a second prompt sent to a still-running session, the optimistic user bubble is removed and its text is returned to the composer for an easy retry.
- **System notices (resume / busy / recovery) render as muted centered pills** instead of masquerading as AI answers with an avatar.
- **Copying a generated script now shows a "Copied ✓" checkmark** for ~1.5 s on the exact button clicked.
- **Deleting a conversation now asks for confirmation** — the small `×` is an irreversible server-side delete and a mis-click shouldn't silently destroy a thread.
- **Per-session context-dedup dictionaries are pruned on session delete** (they previously grew unboundedly over the process lifetime), and each mounted chart's `ResizeObserver` is now disconnected on wipe/unmount instead of observing detached DOM forever.
- **Dead model-selection leftover removed** — the frontend no longer tries to auto-pick an "opus" model from `/api/models`; the backend always chats with its configured deployment and ignores the request's `model` field.

### Added

- **The "Thinking" panel now renders Markdown.** The live reasoning stream was shown as raw plain text; it now runs through the same HTML-escaping `renderContent` renderer as the main answer, so bold headers, bullet lists, inline code, and line breaks in the model's reasoning display properly. Styling is scoped to the panel (`.reasoning-md`) and kept compact + muted so headings/lists/code/tables don't blow up the small rolling-window box, and the rendered HTML is wrapped in a single inner block so the "pin newest lines to the bottom" effect still works. Verified live: a `**bold**` reasoning header rendered as `<strong>` with correct line breaks, no console errors.
- **Sticky auto-scroll + "Latest" pill in the chat.** The messages pane now follows new content through EVERY kind of growth — the "Thinking" reasoning panel appearing and growing (previously never scrolled into view), the intent ticker, streamed text, charts mounting asynchronously, and the viewport shrinking when the composer autogrows or a deck/script card appears (ResizeObserver on the scroll container + content column, plus reactive watchers that keep working in hidden tabs where observer/rAF delivery is suspended). Following is **sticky**: scrolling up to read pauses it (no more being yanked to the bottom mid-read on every delta), scrolling back down or sending a message resumes it, and a floating **"Latest" / "New activity"** pill appears while paused for a one-click return. Switching or restoring a conversation now always lands on the newest message instantly (same-length transcript swaps previously didn't scroll at all, and long transcripts smooth-crawled from the top). Stream-follow scrolling is instant rather than smooth — restarting a smooth animation on every delta frame lagged behind the bottom — and deliberate jumps use smooth only for short hops in a visible document (smooth scrolling never completes in hidden/embedded views). Verified live: pinned through thinking-panel growth 641→747px, no yank while scrolled up mid-stream, pill jump + re-follow, transcript restore lands at bottom.
- **Conversations now survive leaving the page — for everyone.** The active conversation id is persisted (sessionStorage + server-side current-session for Entra users), so a full page reload/navigation restores the transcript automatically — including for anonymous users, whose conversations previously lived only in JS memory. If the page was left mid-answer, the restored view shows a ⏳ reconnecting notice and auto-fills the answer when the server finishes (verified live: reload mid-turn → conversation restored → full answer + table appeared with no user action).
- **Frontend stream-lifecycle telemetry in Application Insights.** New `customEvents` (`chat.stream.start/firstDelta/done/severed/stopped/recovered`, `chat.tab.hidden/visible`, `chat.reattach.recover`, `chat.stream.zombieRecover`, `chat.session.restored`) instrument the chat pipeline end-to-end so background-tab and connection-loss issues are diagnosable from production telemetry (`window.__trackAppInsightsEvent` added in `main.js`).

### Fixed

- **Backgrounding, minimizing, or leaving the window no longer loses the answer.** The backend keeps generating and persists the turn when a client disconnects, but the UI could come back to an empty response or a spurious “Connection lost”. Recovery is now bulletproof and non-destructive: (1) a severed stream recovers by polling the persisted transcript for THIS prompt’s answer (tail-match — instant if it landed while away) and repainting, with a brief refinement watch so mid-turn narration converges to the final answer; (2) a silently-dead “zombie” stream is detected on tab return purely from SERVER state (answer persisted but undelivered one confirm-tick later → abort + recover) — never from client-silence timers, which would kill healthy reasoning pauses; (3) `GET /api/sessions/{id}/messages` now serves anonymous users too (still IDOR-gated per-user), which recovery depends on. Verified live: sever mid-turn → answer recovered; healthy hidden/visible toggle → completes untouched.

### Added

- **Paste or upload screenshots into the chat (vision input).** Images (PNG/JPG/JPEG/GIF/WebP, ≤ 20 MB) can now be attached via the file picker, drag-drop, or pasted straight from the clipboard (Win+Shift+S → Ctrl+V) into the input box. Pasted clipboard images are auto-named `screenshot-<timestamp>.png` and shown as a thumbnail chip. Images bypass the Python analysis helper entirely — they ride along as **native vision attachments** (`MessageOptions.Attachments` → `AttachmentFile` with MIME type) so the model literally sees the screenshot (verified: it read the exact dollar amount off a pasted test image). Each image is consumed by the message it's sent with (delisted server-side after send, chip removed client-side); data files (CSV/XLSX/…) still persist across turns via `QueryUploadedFile`. CSP `img-src` gained `blob:` for the local thumbnail previews.

- **GitHub Copilot SDK 1.0.6 → 1.0.7** with adoption of two new APIs. (1) **`ProviderConfig.BearerTokenProvider`** — the BYOK Azure OpenAI token is now supplied by an on-demand callback the runtime invokes before every model request, replacing the pre-1.0.7 static-token-baked-at-session-creation approach and its ~1h proactive session-recycle workaround (live sessions can now stay up indefinitely; the expiry-based recycle in `GetOrResumeAsync` was removed). (2) **`SessionConfig.ToolSearch = { Enabled = true }`** — explicitly pins tool-search deferral on so the existing `DeferredTool` (`defer=Auto`) cold-path tools keep their ~50% per-request input-token savings across SDK/CLI bumps. Verified live: a plain turn (session+deltas+done, ~3s) and a 2-tool pricing turn (toolStart=2/toolDone=2, streamed, ~14s) both complete on the upgraded stack.

### Fixed

- **Chat input box now grows with multi-line content.** The auto-grow logic set the textarea height from `scrollHeight`, but `.input-field { flex: 1 }` inside the column `.input-wrapper` (flex-basis:0) made the flex layout ignore that inline height and collapse the field to one line. Changed to `flex: 0 0 auto` (width preserved via the wrapper's `stretch`), so the field expands 24px→400px then scrolls (`overflow-y:auto`). Verified live: 1 line=24px, 8 lines=180px, 60 lines=400px+scroll, cleared=24px.
- **Entra account switch no longer leaks the previous account's state.** Signing in with a different Microsoft account on the same browser session used to hand the new account the previous account's ARM/Graph/Log-Analytics/Storage tokens, consent tiers, and active conversation (the anon→Entra in-memory migration also ran on Entra→Entra switches, and per-resource session tokens were never purged). The OAuth callback now detects the OID change, skips the migration, purges every token/tier belonging to the previous account, and repoints (or drops) the `finops_id` identity cookie so hydration can't resurrect the old identity.
- **Base-tier users no longer fire doomed token exchanges on every message.** Every chat request attempted refresh-token exchanges for Graph, Log Analytics, and Storage even when the user only consented to base ARM — each a guaranteed HTTP 400 at `login.microsoftonline.com` plus up to three wasted Entra round-trips of first-token latency per message. `SessionTokenStore` now gates refresh attempts on the consented-tier list (all add-on tiers are recorded in `graph_tier` at consent time, incl. loganalytics/storage) and applies a 15-minute backoff after a failed add-on exchange. Failed exchanges also log the AADSTS `error`/`error_description` instead of silently returning null. _Note: users who consented to Log Analytics/Storage before this change need to re-click the add-on button once (their persisted consent list predates the tier markers)._
- **Streaming no longer freezes when the browser tab is backgrounded.** The typewriter effect drained text via `requestAnimationFrame`, which browsers fully suspend in hidden tabs — the answer looked stalled and crawled at ~600 chars/s after refocus. Text now renders synchronously while the tab is hidden and the pending animation queue is flushed on `visibilitychange`.
- **Opening a past conversation whose CLI state is gone returns an empty transcript instead of HTTP 500** (`GET /api/sessions/{id}/messages` threw `RemoteRpcException: Session not found` when the session listing and on-disk state disagreed).

### Fixed

- **Stale-session recovery for chat turns — no more hard error _or_ silent hang.** Two related gaps in the SSE chat path when the CLI had evicted a session between turns (the first confirmed via stack trace at `ChatEndpoints.cs`): **(1)** the per-turn effort switch (`session.model.switchTo`) ran _before_ the streaming subscriptions and threw `Session not found` uncaught, surfacing a raw error to the user; **(2)** the `SendAsync` recycle reassigned the session handle but left the SSE subscriptions bound to the _dead_ one, so a recycled turn generated server-side yet never streamed to the browser. Both now recover: the effort switch recycles **before** subscriptions are wired, and the `SendAsync` path detaches and **rebinds** the subscriptions (`WireHandlers`) onto the live session, re-announcing the session id so the frontend keeps streaming into the right conversation. Verified: happy-path streaming (text, tool calls, chart, first-event timing, completion) is fully regression-clean through the refactored subscription wiring; the recovery branches are correct-by-construction and reuse that same proven wiring, but the underlying staleness is a non-deterministic race (idle-disconnected sessions transparently auto-reconnect from disk) that could not be force-fired in re-tests.
- **Sidebar titles no longer leak prompt scaffolding** — when the SDK truncated a long first prompt mid-`[CONTEXT: …]` block, `CleanSummary`/`StripContextPrefix` surfaced the raw injected context (e.g. "[CONTEXT: User is NOT…") as the conversation title. Truncated context blocks are now discarded entirely.

Now uses the modern `/openai/v1/chat/completions` surface with `reasoning_effort: "low"` and 512-token headroom (verified: 8 completion tokens, 0 reasoning tokens).

The system prompt now mandates three `SuggestFollowUp` starter actions (public pricing actions when not connected; scoring/cost/idle actions when connected).
