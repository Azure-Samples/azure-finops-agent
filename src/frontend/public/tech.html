Warm-up, about four minutes. Five AI assistants got the same question: what is the weather in Copenhagen? Clicks 1 to 5 reveal one lane at a time. Ask the room to hold up 0 to 5 fingers, or type the score in the Teams chat. Point at the tool calls column: that is the evidence. Don't explain anything yet; most people score 2 and 4 too high because the answers sound sure, and 5 splits the room: honest, but no weather. Clicks 6 to 10 stamp the judge's score on each lane. Compare it with the room. 1 gets 5: it asked the weather service, then answered. Right, checked and quick. 2 gets 0: no tool, no data, so it made the weather up. 21 degrees and sunny in Copenhagen in November gives it away. Sounding sure is not the same as being right. 3 gets 2: the answer is right, but it asked the weather service four times for one answer: four times the cost and the waiting. My release gate would fail it. 4 gets 1: the tool failed and the answer pretends it didn't. Something unknown became a fact. If someone says that is worse than 2: fair, hiding a failure you saw is deception. It gets 1 only because it at least called the tool. 5 gets 3: the tool failed and it said so. Honest beats any guess, but it didn't solve the problem: you still have no weather. A 5 would try once more and then point you to another source, such as dmi.dk. If someone asks why it scores above answer 3, which did give the weather: answer 3 pays four times for every question, while answer 5 met a broken tool once and told the truth. Last click: a good answer is right, checked, quick and honest. Every release of my agent must pass 23 real questions scored like this, and that is the next part. The small names under the four words are Microsoft Foundry's built-in evaluators, judges anyone can run on their own agents. Right is Task Completion: a usable result. Checked is Groundedness: every claim backed by what the tool returned. Quick is Efficiency, in full Task Navigation Efficiency: no wasted steps. Honest is Task Adherence: the agent kept to its instructions, here check the tool, never guess, and say when it fails. So answer 2 fails Groundedness, 3 Efficiency, 4 Task Adherence and 5 Task Completion. Researchers call an honest "I don't know" abstention, and Anthropic named the overall goal "helpful, honest and harmless" in 2021. Why honest scores above a guess but below a real answer: OpenAI showed in 2025 ("Why Language Models Hallucinate") that most tests score "I don't know" like a wrong answer, so models learn to guess.

Three boxes. You ask in plain words. The agent is a .NET 10 app on Azure App Service, built on Microsoft Agent Framework: one agent serves every chat, using each user's own sign-in. It thinks with a model in Microsoft Foundry, today gpt-6.1-terra through the Responses API, called with a managed identity. The model writes each API call itself, and the tools stay thin: QueryAzure reads Azure Resource Manager, Microsoft Graph, Log Analytics, the Retail Prices API and documentation. Microsoft Learn comes through its MCP server. GenerateScript and GenerateDataReport make files, and ApplyAzureChange only runs after the user approves the exact request. The safety rules live in the code, not in the prompt: DELETE is blocked, POST is allow-listed, writes wait for approval, and every answer shows its calls. Built with GitHub Copilot: over 700 commits since 15 March, over 300 of them co-authored with Copilot, and 13 repo skills that deploy, release, evaluate sessions and investigate logs.

Part 1 · Offline evaluation

Nothing ships until 23 questions pass.

  2. Ask 23 real questions

  4. Release
One failure stops the release.
80%+AI judges agree with people as often as people agree with each other.Zheng et al., NeurIPS 2023
Every push runs 341 C# tests and desktop and mobile browser tests. Then the live gate: 23 real questions, each in a fresh process, on the real model and real Azure tools. A second model, gpt-6.1-sol, judges every answer: accepted, grounded, complete and efficient, with 19 fixed reason codes, like the ones in the warm-up. Code checks override the judge, and the code turns the judge's waste counts into the efficiency score. One failure stops the deployment, with no re-run. A failed eval is fixed at its cause: never by re-running it, switching models or loosening the rubric. Then the test slot, production, a smoke test and automatic rollback. After that comes the second phase, the quality report: next slide. The theory: Zheng et al., NeurIPS 2023, "Judging LLM-as-a-Judge": strong LLM judges agree with human preferences over 80% of the time, as often as humans agree with each other. They also favour answers by position, by length and their own style, which is why a different model judges and code checks override it. A real example from this week: the gate stopped my own release. I had added a Microsoft 365 Copilot trial to my test tenant, so one of the 23 questions, which users haven't used Copilot in 30 days, could no longer be answered: the tenant has no Microsoft 365 usage reporting at all. The agent said so honestly, like answer 5 in the warm-up, and the judge marked the answer incomplete, so the release could not ship. The fix was a written rule, not a re-run: when the host proves the tenant has no usage reporting, an answer that gives the seats and says exactly that is complete. It happened again on Thursday, five times, to my own change for shorter answers. The gate and the quality report rejected five different evals: one note said a database's 500 GB "includes 150 GB of log", where Azure bills 500 GB of data plus 150 GB of log; one turned a 20% premium into "20% less", which is 16.5%; one said the rows a table left out held "another USD 542 estimate" that the table already showed. Every figure the agent computed was right; each failure was a fact reworded to fit a shorter answer. Patching each wording only let the next one appear, so the fix became one principle in the prompt: shorten by leaving things out, never by rewording what stays. After that, and one more fix for a call it made that it didn't need, all 23 gate evals and all 15 report evals passed. That is the lesson: when evals keep failing in different places, look for the one cause. And the day after GPT-6.2 sol launched at Ignite, I ran the 15 quality evals on it before anything else: all 15 failed on the first request, because Foundry's project API doesn't yet accept web search, reasoning effort or an input over 10,000 tokens for the new model. The account endpoint accepted all of it and answered a test question 1.8 times faster, so the agent now calls the account endpoint, and on Wednesday night GPT-6.2 sol ran the same 15 evals as terra on the same build: terra passed all 15, while 6.2 sol failed one of the first eight it ran, an unsupported and incomplete answer to "How do I find all our AI agents?", which terra passes, and it was not faster across the board. On Thursday I compared them again on five evals with the shorter answers: 6.2 sol failed a different one, best value, where it took 76 seconds and 13 calls against terra's 36 seconds and 6. Faster on one test question is not better, so production stays on GPT-6.1 terra. That is why a new model goes through the evals, not straight to production. I'll show what the gate held back in Part 2.

Two evaluation phases run on every push to main. Click by click: the push, phase 1, the deployment, phase 2, then why there are two. Phase 1, the live gate, runs before anything ships, alongside the C# tests, desktop and mobile browser tests and the Linux image with its vulnerability scan. 23 curated questions, the start-page cards and past incidents, run on the real model and real Azure tools, and a second model, GPT-6.1 sol, judges every answer. All 23 must pass: one failure stops the release, and it is fixed at its cause, never re-run. Then the build deploys, a smoke test asks it a question through the public URL, and a failure there rolls back automatically. Wednesday night's run took 17 minutes from push to production. Phase 2, the AI quality report, starts after every successful deployment, every Monday and on demand. It runs 15 more evals in four stages side by side: cost, the most-asked start-page cards, safety and other languages. It is green at 80%, a documented limitation shows amber instead of red, and it never blocks a release, so it can hold newer and harder questions. Its inputs run another model or reasoning effort for one run: that is how GPT-6.2 sol was compared with terra on the same commit, and failed. Why two: every gate eval can stop a release and spends the tenant's small Cost Management quota, so the gate keeps only stable essentials. An eval that keeps passing in the report is promoted into the gate. The theory, if someone asks whether phase 2 is online evaluation: no. Offline or online is about who wrote the question, not when or where it runs. Both phases ask questions I wrote, and both run the released commit in a test host on the build server, with an evaluation identity on a lab tenant, never on the live site or with real users. A question I wrote can only catch failures I already thought of; real users bring the ones I didn't. Even a scripted question sent to the live site, like the smoke test after each deploy, is synthetic monitoring, not online evaluation. Microsoft Learn's "Observability in generative AI" calls phase 1 pre-production evaluation, and lists phase 2 under post-production monitoring as scheduled evaluation: "scheduled quality and safety evaluation using test datasets to detect system drift". My code doesn't change on a Monday, but Azure's APIs, prices and documentation do. Online evaluation, which Learn calls continuous evaluation of production traffic, is the next slide: real users' conversations. Another real example, from Wednesday night: the quality report failed the FinOps assessment card. It grouped the month's cost by the CostCenter tag but read a column named CostCenter, while Cost Management returns a tag grouping as TagKey and TagValue. The host read the missing column as empty, so the report called the month's cost untagged without evidence, and the judge rejected it as ungrounded. The fix went into the host, not a re-run: a column a table doesn't have now fails with the table's real column names, so no answer can be built on it.

Every AI bill is tokens times price, so there are only two kinds of lever: a cheaper price, or fewer tokens. Cheaper model: pick the model by cost per answer, not price per token. Moving to gpt-6.1-terra halved the token price and cut the cost per answer to 41%, a 59% saving. The median answer went from 58 to 28 seconds, and it passed the same 23 questions first. Cache it: instructions and tool definitions ride along on every model call, about 27,000 tokens, but they are the same every time, so Foundry caches them. 77% of production's input tokens come from the cache at 5% of the input price, and a cached 15,000-token system prompt answers as fast as a 1,700-token one. So I don't cut rules to save tokens; I cut what changes: a turn only gets the tools it can use, and a long chat starts fresh after 100,000 tokens, because calls above 180,000 tokens waited 10 to 17 seconds for the first word. Think less: one round took about 45 seconds at extra-high reasoning effort and 15 at medium. Write less: output tokens are the slow and expensive part. One maturity assessment wrote about 8,000 tokens, so answers now aim for 150 words and one table. On Thursday I went further: every answer is short and precise however much research it took, with at most three one-line notes and never more than 120 words besides its table or chart. Over five evals the words outside the table fell by 28%, and all five still passed.

A quick quiz. Click: Agent 365, Microsoft's control plane for AI agents: one registry to see, govern and secure every agent, whoever built it. Its registry lists Copilot Studio agents, published Foundry agents, and agents on Amazon Bedrock or Google Vertex AI once you connect those platforms. Click: the Responses API, the newer API and the one Microsoft recommends for new apps. It's stateful: pass previous_response_id and it carries the conversation for you. And it has built-in tools: web search, file search, code interpreter and MCP servers. Click: Chat Completions, the classic. Stateless: you send the whole conversation with every call. Still supported, and it works with almost every model and SDK. One catch for agents: on the newest reasoning models, a Chat Completions call with function tools fails unless you turn reasoning off, so Microsoft Learn points you to the Responses API for tool calling. That's why my agent uses Responses. Click: the question. My app uses these APIs with tools and memory: it plans, calls tools and remembers. What does Agent 365 show? Hands up if it shows up in the registry. Wait for the hands. Click: Nothing. Wrong. Until you register it, Agent 365 doesn't see an agent: it's a model endpoint, tokens in and tokens out, running as your app's key or managed identity, with no agent identity. Microsoft Learn even calls this an ephemeral agent: when you call the Responses API directly, there is no agent to create, update or delete. It's the Non-agent requests row from the Foundry screenshot: 63 percent of that project's token cost, with no traces linked. Honest footnote: my own FinOps agent is one of these today. It calls the Responses API with its web app's managed identity, so Agent 365 doesn't list it. If someone pushes back: calling a published Foundry agent through the Responses API, with agent_reference, does run as that agent. And Defender's discovery of local agents covers managed devices, not a server calling a model.

Gotcha: creating an Entra identity alone doesn’t register the agent.

So what changes when you register it? Row by row. Identity: a model call runs as your app, with its key or managed identity. A registered agent gets its own Microsoft Entra agent identity. Agent 365: the model call isn't listed. The agent is in the registry, with an owner. Security: a model call can do whatever your app is allowed to. An agent identity gets Conditional Access and identity protection, which need Entra Agent ID licensing, and Defender and Purview see the same agents. Cost: in Foundry, model calls land in Non-agent requests. An agent gets its own row, with its traces linked. Click: three ways to register. Built in Foundry: publish the agent and it appears in the Agent 365 registry automatically, with its own agent identity. Copilot Studio agents are there the moment you create them. Your own code: the Agent 365 CLI, a365 setup all, registers a blueprint and an agent identity, and the Agent 365 SDK adds notifications, Work IQ tools and observability through Microsoft OpenTelemetry. Bedrock or Vertex AI: connect the platform in Agent 365 and its agents sync, with no development work. Click: the gotcha. Creating a Microsoft Entra identity alone doesn't register the agent instance. You still need the registration step. Don't run the Copilot or cost cards in the ten minutes before you present: Microsoft Graph's Copilot cost API and Azure Cost Management throttle a burst of requests (Cost Management allows 12 query units per 10 seconds per tenant), and a throttled answer shows a countdown while it waits. 1.
