Warm-up, about four minutes. Five AI assistants got the same question: what is the weather in Copenhagen? Clicks 1 to 5 reveal one lane at a time. Ask the room to hold up 0 to 5 fingers, or type the score in the Teams chat. Point at the tool calls column: that is the evidence. Don't explain anything yet; most people score 2 and 4 too high because the answers sound sure, and 5 splits the room: honest, but no weather. Clicks 6 to 10 stamp the judge's score on each lane. Compare it with the room. 1 gets 5: it asked the weather service, then answered. Right, checked and quick. 2 gets 0: no tool, no data, so it made the weather up. 21 degrees and sunny in Copenhagen in November gives it away. Sounding sure is not the same as being right. 3 gets 2: the answer is right, but it asked the weather service four times for one answer: four times the cost and the waiting. My release gate would fail it. 4 gets 1: the tool failed and the answer pretends it didn't. Something unknown became a fact. If someone says that is worse than 2: fair, hiding a failure you saw is deception. It gets 1 only because it at least called the tool. 5 gets 3: the tool failed and it said so. Honest beats any guess, but it didn't solve the problem: you still have no weather. A 5 would try once more and then point you to another source, such as dmi.dk. If someone asks why it scores above answer 3, which did give the weather: answer 3 pays four times for every question, while answer 5 met a broken tool once and told the truth. Last click: a good answer is right, checked, quick and honest. Every release of my agent must pass 23 real questions scored like this, and that is the next part. The small names under the four words are Microsoft Foundry's built-in evaluators, judges anyone can run on their own agents. Right is Task Completion: a usable result. Checked is Groundedness: every claim backed by what the tool returned. Quick is Efficiency, in full Task Navigation Efficiency: no wasted steps. Honest is Task Adherence: the agent kept to its instructions, here check the tool, never guess, and say when it fails. So answer 2 fails Groundedness, 3 Efficiency, 4 Task Adherence and 5 Task Completion. Researchers call an honest "I don't know" abstention, and Anthropic named the overall goal "helpful, honest and harmless" in 2021. Why honest scores above a guess but below a real answer: OpenAI showed in 2025 ("Why Language Models Hallucinate") that most tests score "I don't know" like a wrong answer, so models learn to guess.

Three boxes. You ask in plain words. The agent is a .NET 10 app on Azure App Service, built on Microsoft Agent Framework: one agent serves every chat, using each user's own sign-in. It thinks with a model in Microsoft Foundry, today gpt-6.1-terra through the Responses API, called with a managed identity. The model writes each API call itself, and the tools stay thin: QueryAzure reads Azure Resource Manager, Microsoft Graph, Log Analytics, the Retail Prices API and documentation. Microsoft Learn comes through its MCP server. GenerateScript and GenerateDataReport make files, and ApplyAzureChange only runs after the user approves the exact request. The safety rules live in the code, not in the prompt: DELETE is blocked, POST is allow-listed, writes wait for approval, and every answer shows its calls. Built with GitHub Copilot: 664 commits since 15 March, 264 of them co-authored with Copilot, and 13 repo skills that deploy, release, evaluate sessions and investigate logs.

The three stages come from Microsoft Learn: “Observability in generative AI”.

The theory has a name: GenAIOps, or LLMOps, which is DevOps for AI apps. Not AIOps, which means AI for IT operations. Microsoft Learn's "Observability in generative AI" names three stages: base model selection, pre-production evaluation and post-production monitoring. 1. Pick the model: every candidate model runs the same 23-question gate. gpt-6.1-terra won: 41% of the cost per answer and twice as fast. 2. Test before release: the offline evaluation in my deploy workflow, next slide. 3. Watch real use: OpenTelemetry traces in Application Insights, and scoring real conversations, the slide after. The flywheel: what fails online becomes an offline test case, so every later release is checked for it.
Part 1 · Offline evaluation

Nothing ships until 23 questions pass.

  1. Push code
  2. Ask 23 real questions
  3. An AI judge scores each
  4. Release
One failure stops the release.
80%+AI judges agree with people as often as people agree with each other.Zheng et al., NeurIPS 2023
Every push runs 339 C# tests and desktop and mobile browser tests. Then the live gate: 23 real questions, each in a fresh process, on the real model and real Azure tools. A second model, gpt-6.1-sol, judges every answer: accepted, grounded, complete and efficient, with 19 fixed reason codes, like the ones in the warm-up. Code checks override the judge, and the code turns the judge's waste counts into the efficiency score. One failure stops the deployment, with no re-run. A failed eval is fixed at its cause: never by re-running it, switching models or loosening the rubric. Then the test slot, production, a smoke test and automatic rollback. After every deploy and every Monday, a quality report runs 15 more evals with an 80% bar, and it also stops at the first failed eval, so a red run wastes no time. The theory: Zheng et al., NeurIPS 2023, "Judging LLM-as-a-Judge": strong LLM judges agree with human preferences over 80% of the time, as often as humans agree with each other. They also favour answers by position, by length and their own style, which is why a different model judges and code checks override it. A real example from this week: the gate stopped my own release. I had added a Microsoft 365 Copilot trial to my test tenant, so one of the 23 questions, which users haven't used Copilot in 30 days, could no longer be answered: the tenant has no Microsoft 365 usage reporting at all. The agent said so honestly, like answer 5 in the warm-up, and the judge marked the answer incomplete, so the release could not ship. The fix was a written rule, not a re-run: when the host proves the tenant has no usage reporting, an answer that gives the seats and says exactly that is complete. And the day after GPT-6.2 sol launched at Ignite, I ran the 15 quality evals on it before anything else: all 15 failed on the first request, because Foundry's project API doesn't yet accept web search or reasoning effort for the new model. Production stayed on GPT-6.1 terra. That is why a new model goes through the evals, not straight to production. I'll show what the gate held back in Part 2.

Online evaluation is a repo skill I run every few weeks with GitHub Copilot. It exports up to 30 days of real conversations, read-only and pseudonymised, without my own use and the smoke tests. The production model scores every conversation from 0 to 10 against a fixed rubric, with nothing stored. I read the 5 lowest and 3 highest myself. Rating the same records twice changed 30 of 107 scores, so I average two runs. Then I group the problems by cause, trace each one in the code, check API facts in the docs, fix it and add a test. Real failures become eval cases. Latest audit, 16 November, 14 days: 48 conversations from 37 people in 14 countries. The most typed request became the "Price my own setup" card, signed-in users got a "FinOps assessment report" card, three cards nobody clicked were removed, and two more evals joined the quality report.

Every AI bill is tokens times price, so there are only two kinds of lever: a cheaper price, or fewer tokens. Cheaper model: pick the model by cost per answer, not price per token. Moving to gpt-6.1-terra halved the token price and cut the cost per answer to 41%, a 59% saving. The median answer went from 58 to 28 seconds, and it passed the same 23 questions first. Send less: instructions and tool definitions ride along on every model call, about 27,000 tokens. Now a turn only gets the tools it can use, and a long chat starts fresh after 100,000 tokens, because calls above 180,000 tokens waited 10 to 17 seconds for the first word. Think less: one round took about 45 seconds at extra-high reasoning effort and 15 at medium. Write less: output tokens are the slow and expensive part. One maturity assessment wrote about 8,000 tokens, so answers now aim for 150 words and one table.

When a customer asks what AI costs, the honest answer is: which of the four meters? Per user: Microsoft 365 Copilot licences. The waste is licences nobody uses; the agent reads the Copilot usage reports through Microsoft Graph. Per seat plus AI credits: GitHub Copilot. Watch the seats and set a budget for the credits. Copilot Credits: Copilot Studio, Cowork, Work IQ API and agents. Governed in the Microsoft 365 admin center under Copilot, Cost management. Pay-as-you-go credits are billed to an Azure subscription, so they also show up in Azure Cost Management. Per token: Foundry models, billed on input, cached input and output tokens, or provisioned throughput by the hour. The start-page card "How do we budget and justify AI?" answers all four in one table.

Ask:What did my Copilot work cost?
New this week. At Ignite on 17 November, Microsoft announced Agent 365 Cost Management in the Microsoft 365 admin center, with a Microsoft Graph API (beta, under /copilot/costManagement): Copilot Credits per user, security group and service, each user's balance and sessions, the spending policies and credit requests. It reports credits, not currency. The agent reads all of it now, in preview, and the start page has five new Copilot cards marked Preview. The story to tell: this week I built a small website with Code, the Microsoft 365 Copilot service the admin center lists as Code. "What did my Copilot work cost?" lists each of today's sessions with its times and credits, per service, named as the admin center names them, and prices them at the pay-as-you-go list price of USD 0.01 a credit, which it reads from the Azure Retail Prices API: a few hundred credits is a few dollars. One thing to know: Graph lists only the services a policy names explicitly, while the admin center also counts services a policy covers through Auto-apply new services, so Code, which no policy lists, is still counted under the all-users policy; the agent reads the raw usage, which lists every service. The money is on the Azure bill: pay-as-you-go Copilot credits for Cowork, Code and Work IQ are billed to an Azure subscription as Microsoft Copilot Studio, usually within a day, so the agent puts that bill next to the credits. Per model and per agent, in dollars, comes from Azure Cost Management too: Foundry tags model usage with the deployment, and from November with agent.name when an agent made the call. The API has no per-service count of users or sessions, so for a big tenant those columns cover the users the agent read, and it says so. It is in the release after this week's gate; if that isn't live on azure-finops-agent.com yet, demo it from the local build.

Click by click: the two Copilot rows, where both tools now answer and the agent changes limits only with your approval, then four where only the agent answers, then the verdict. Agent 365 Cost Management, in the Microsoft 365 admin center under Copilot, Cost management, is the control plane for Copilot Credits: who uses them, spending policies and limits for users, groups and agents, alerts and credit requests. Everything there is in Copilot Credits, not currency. Business Analytics adds dollars, in preview: November for Cowork, December for agents. The agent is the analyst. It now reads the same Copilot data: credits per user, per service and per session, each user's balance under its spending policy, and the limits themselves. With a second consent, Copilot Cost Changes, it can also change a limit or decide a credit request, but only after you approve the exact request, and it never deletes. Its answers use the admin center's own names: the views Policies, Users & groups and Services & agents, their columns, and each service as the admin center lists it (Code, Cowork, Opal, Copilot Managed Runtime). Microsoft Graph reports services per completed day and has no per-service user or session counts, so today's usage that no user made shows up in the next day's report; until then the agent says so in a note and writes Unavailable where Graph has no value, as the admin center does. Azure Cost Management already shows Copilot pay-as-you-go charges in money, under Microsoft Copilot Studio (prepaid capacity packs are not there). The agent reads that next to all Azure and Foundry cost, machine utilization from Log Analytics, Microsoft 365 licences and Copilot usage, Advisor and list prices, joins it in one overview, and every answer shows the calls behind it. It is free and open source under the MIT licence: you pay only for the Azure it runs on, and anyone can read every line. Trust can't be sold. They don't compete: set the limits in the admin center, then ask the agent why the bill moved and what to change.
